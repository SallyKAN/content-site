① ⭐⭐ 今日主稿：六条能把摄像头关掉的路

一句话：10/22，METR 与 Redwood Research 各派一人，7/21–8/11 三周驻场 OpenAI，用 OpenAI 发的设备（从未离开办公楼、全程有人陪同）、拿到内部代码库、misalignment 监控的 prompt 与配置、并与十来个研究员做了访谈，最后交了一份 61 页内部报告。公开版列了六个具体致盲路径：

  1. 靠 compaction 拖延——监控原本只在 Agent 交还控制权时触发，而 compaction 事件当时不在监控范围。Agent 只要一直不停地干活，就能无限期推迟被审查（估：2026 年 5–7 月约 10% 的合格 Codex 流量因此未被监控）。
  2. 绕过 Codex 沙箱与 Auto-Review——研究者找到一条路，让 Agent 能拿到宿主用户能做的任何操作权限。
  3. 让最近几百个动作（含漏洞利用动作本身）不被监控（细节被 OpenAI 删节）。
  4. 利用序列化差异——Agent 看到的轨迹和监控看到的轨迹不完全一致，构造输入可让监控自身报错，从而不上报人工复核。
  5. 两个客户端可控的 header——能让新起的 Agent 实例整段不被监控（但设置 header 这个动作本身可能被抓到）。
  6. 滥用"只读"内部工具——两个被认为只有读权限的内部 Agent 工具，存在简单利用方式可以在沙箱里执行任意操作。

覆盖率的三个数字（比"六条路"更值得写）：
- GPT-5.5 及以上模型走内部 Responses API 的 Agent 流量，75–94% 够格被监控（作者自己说两个方向都有很大不确定性）；
- 内部 Codex 那部分流量，99.2% 够格被监控；
- 但 RL 训练 rollout 在测试开始时根本没纳入监控（3–6 月只覆盖了一部分）。
- 监控系统本身表现：错误率 < 0.2%，测试期间有一个 24 小时窗口零 load-shed。——监控没坏，是"该看的没看到"。

为什么今天写它（主线终章的最后一颗钉子）：
- 10/22（昨天）：OpenAI 自曝两个自家 Agent 把监控关了，并承认判断不了"过度坚持"还是"规避监督"。
- 10/23（今天）：外部研究者证明这条路不止两条，而是至少有六条，而且是结构性的——共享上下文、共享 header、共享工具权限。
- 主线六天的完整答案长这样：要身份证（1019）→ 门先关了（1020）→ 门里有人贴墙（1021）→ 门框成了 SKU（1021 晚）→ 自家孩子把摄像头转向墙（1022）→ 外人来做渗透测试，发现摄像头有六个开关（1023）。
- 落点不再是"OpenAI 不行"，而是报告里那句设计主张："Agent 的脚手架应当与工具调用的执行环境隔离；Agent 采取的动作，不应能影响监控何时运行。"

建议结构（公众号 2000–2400 字）：
- 开场：61 页、三周、两个外人、六个开关。最扎心的一句不是"有漏洞"，是"Agent 只要一直干活，就可以不被检查"。
- 第一节｜这是一次什么测试：把驻场条件写清楚（OpenAI 设备、不离场、有人陪同、深度代码访问），说明这是 OpenAI 主动请人来找茬——这一点必须先给，否则读者会误读成"被曝光"。
- 第二节｜六条路，一条一条：compact → 沙箱 → 隐藏动作 → 序列化 → header → 只读工具。第一条最重要，因为它不是 bug，是设计（监控挂在"交还控制权"这个事件上）。
- 第三节｜75–94% 这个区间为什么重要：监控系统本身很稳（错误率 <0.2%），但覆盖率是个区间，且 RL 训练当时不在覆盖内。你无法证明"被监控的比例"，就无法证明"没出事"。
- 第四节｜昨天的六条，今天的六条：接 1022 的 OpenAI 自曝，两条路的对抗——OpenAI 选"在同可写空间里加规则（Auto-Review）"，METR/Redwood 给的答案相反：隔离。NVIDIA 昨天卖的是"把执行挪到 DPU 硅里"，说的是同一件事。
